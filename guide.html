Personal Access Token (PAT) Management

When you first open the application, a modal will appear asking you to enter your Azure DevOps Personal Access Token.

How to get your PAT:
  1. Go to Azure DevOps → User Settings → Personal Access Tokens
  2. Click "New Token"
  3. Select scope: Work Items: Read (for read-only) or Work Items: Read & Write (for creating work items)
  4. Copy the generated token
  5. Paste it in the PAT modal and select the matching permission level

Changing your PAT: Click the key icon next to the permission badge to open the PAT modal and enter a new token.

Your PAT is stored securely in your browser's local storage and is never sent to any server except Azure DevOps API.

Read-Only vs Read-Write Mode

The application supports two permission modes, indicated by a badge next to the Last reload info:

  • Read-Only - View work items, export PDFs, but cannot create new work items or view child tasks
  • Read-Write - All read-only features plus:
    • Ability to create new work items using the button
    • Access to Task Mode for viewing and creating child tasks
Important:

When entering your PAT in the modal, you must select the permission level that exactly matches your token's scope in Azure DevOps:

  • If your token has Work Items: Read scope → select Read-Only
  • If your token has Work Items: Read & Write scope → select Read-Write

Warning: If you select Read-Write but your token only has Read permissions, the create work item buttons will be visible, but creating work items will fail with permission errors.

Reload Data

Click the Reload button to:

  • Fetch the latest work items from Azure DevOps
  • Update progress bars with current completion status
  • Refresh all release, major, and patch versions

The application displays Last reload time below the buttons (e.g., "Last reload: 2 hours, 15 minutes ago"). This time updates automatically every minute.

Use reload when you want to see the most up-to-date information.

Which Work Items are Displayed

The application displays only work items that meet the following criteria:

  • Type: Only Feature and Bug work item types
  • Platform Release: Work items must have the Custom.PlatformRelease field populated with the corresponding release (e.g., "Labe-07.006")
  • Status:
    • All statuses except Removed
    • Work items with Closed status are only shown if they were closed within the last 180 days
Note:

Older closed work items (>180 days) are not displayed to keep the overview clean and focused on recent work. All work items can be found in Azure DevOps.

Clicking a work item title now opens the Work Item Detail modal instead of navigating directly to Azure DevOps. You can still open the item in DevOps using the Open in DevOps button inside the detail modal.

Work Item Detail

Click any work item title (Feature, Bug, or Task) to open a detail modal with the most important information.

  • Lazy-loaded Description: The description is loaded when the modal opens to improve performance. HTML content (including images) is rendered as-is from Azure DevOps.
  • Meta badges: Status, Priority, Severity, Version and Assigned To are shown with the same colors and styles as in the main view.
  • Copy Title: Use the copy icon next to the work item title to copy the title to clipboard in Conventional Commits format (e.g., "feat(): 123 feature name" or "fix(): 456 bug name").
  • Edit Title and Description (Read-Write Mode only): In read-write mode, you can edit the work item title and description directly in the modal. The description editor includes a rich text toolbar for formatting (bold, italic, lists, links, etc.). You can paste screenshots directly into the description (Ctrl+V / Cmd+V), and they will be automatically uploaded as attachments to Azure DevOps when you save.
  • Update Button: After editing title or description, click the "Update" button to save your changes to Azure DevOps.
  • Open in DevOps: Use the button in the modal footer to open the item directly in Azure DevOps in a new tab.
Tip:

The title on the main screen no longer navigates to DevOps. This avoids accidental navigation and keeps your context within Releasy.

Note:

Editing is only available when using a read-write token. In read-only mode, the title and description fields are not editable.

Understanding the Hierarchy

The application displays releases in a 4-level hierarchy:

  • Level 1 (Product - Release): e.g., "Xeelo - Labe"
  • Level 2 (Major Version): e.g., "Labe-07"
  • Level 3 (Patch Version): e.g., "Labe-07.005"
  • Level 4 (Work Items): Features and Bugs

Click on any level header to expand/collapse it. Your expansion state is saved automatically.

Progress Bars

Color-coded progress bars show work item status distribution:

  • Closed - Completed work
  • Resolved - Ready for verification
  • Active - Currently in progress
  • New - Not started yet
  • Evaluation - Needs attention

Hide/Unhide Versions

Hiding Versions

You can hide products, major versions, or patch versions to focus on what matters:

  • Products: Hover over any product header (e.g., "Xeelo - Labe") to see the icon. Click to hide the entire product and all its versions.
  • Major Versions: Hover over any major version header (e.g., "Labe-07") to see the icon. Click to hide that major version and all its patches.
  • Patch Versions: Hover over any patch version header (e.g., "Labe-07.006") to see the icon. Click to hide that patch version.
  • Click the icon to hide that element (no reload needed)
  • Hidden elements are excluded from progress bar calculations
Unhiding Versions

The Unhide (X) button displays the number of hidden elements (products, major versions, and patch versions).

  • Click to open a dialog with all hidden elements organized by type
  • Select which elements you want to unhide using checkboxes
  • Use Select All / Deselect All for bulk selection within each group
  • Click Show Selected to unhide chosen elements

Expand All / Collapse All

  • Expand All: Expands all releases and major versions (patches stay collapsed)
  • Collapse All: Collapses everything to the top level

Filter Work Items

Use the Filter button to narrow down displayed work items based on assignee and status:

  1. Open Filter Modal: Click the filter button in the control panel
  2. Select Assignees: Check/uncheck assignees to show only their work items
    • Use the green button to select all
    • Use the red button to deselect all
  3. Select Statuses: Check/uncheck statuses to filter work items by their current state
  4. Apply Filters: Click the Apply button to activate your filters
  5. Remove Filters: Click Remove Filter to clear all active filters
Important:
  • The filter modal shows only assignees and statuses from currently visible work items (excludes hidden patch/major versions)
  • Active filters are indicated by an orange dot on the filter button
  • Your filter settings are automatically saved and restored when you reload the page
  • Filters work with the hierarchical structure - empty sections are automatically hidden

Export to PDF

Export patch version details to a professional PDF document:

  • Hover over any patch version header to see the icon
  • Click the icon to export that specific patch version to PDF
  • PDF includes: version info, statistics, and complete work items table
  • Perfect for stakeholder presentations and release documentation

Task Mode - Viewing Child Tasks

In Read-Write mode, the Task Mode button allows you to show or hide child tasks for all visible Bugs and Features:

  1. Activate Task Mode: Click the button in the control panel
    • Available only in Read-Write mode
    • Active state is indicated by a brown button background
    • Your preference is automatically saved
  2. Display Child Tasks: When activated, child tasks appear under each Bug or Feature
    • Tasks are loaded efficiently from Azure DevOps
    • A spinner shows on the button during loading
  3. Visual Design: Child tasks are visually distinct:
    • Indented with a brown left border
    • Smaller, italic text with a light brown background
    • Brown icon
    • Show: icon, title, assigned person, and status
    • Not collapsible (displayed as a flat list)
  4. Sorting: Child tasks are automatically sorted:
    • First by status: Evaluation → New → Active → On Hold → Closed
    • Then alphabetically: By title within the same status
  5. Filtering: When Task Mode is active, filters use OR logic - a work item is shown if either the parent OR any child task matches the filter criteria
  6. Deactivate: Click the button again to hide all child tasks
Important:
  • Task Mode works only for visible work items (respects filters and hidden versions)
  • Child tasks are reloaded when filters change or after data reload
  • Task Mode state persists across page refreshes
  • Tasks with "Removed" status are not displayed
  • Loading may take a few seconds for large datasets

Creating Work Items

When in Read-Write mode, you can create new work items directly from the application:

Prerequisites:
  • Your PAT must have Work Items: Read & Write scope
  • You must select Read-Write permission when entering your PAT
  • The button will appear next to PDF export on patch versions

How to create a work item:

  1. Open the modal: Hover over any patch version header and click the icon
  2. Select Work Item Type: Choose between Feature or Bug
  3. Fill in Title:
    • Select a prefix from the dropdown (e.g., "Xeelo", "Xeelo mobile", "Xeelo admin", "Integray", "Repository")
    • The prefix is automatically added based on the product context
    • Enter the main title in the text field (e.g., "calendar week start day")
    • Final title will be: Prefix - Your Title (e.g., "Xeelo mobile - calendar week start day")
  4. Description (optional): Add detailed information about the work item
  5. Assigned To: Select an assignee or leave as "Unassigned" (default)
  6. Priority: Set priority from 1 (Critical) to 4 (Low) - default is 3 (Medium)
  7. Severity (Bugs only): For bugs, set severity from 1 (Critical) to 4 (Low) - default is 3 (Medium)
  8. Review & Submit: Check the patch version info at the bottom and click + Create Work Item

After creation:

  • A success modal will display with the Work Item ID and details
  • Click Open in DevOps to view the work item in Azure DevOps
  • The work item is automatically linked to the appropriate Epic based on the release
  • The platform release (e.g., "Labe-07.006") is stored in the custom field Custom.PlatformRelease
  • The product (e.g., "Xeelo") is added as a tag
  • The page will automatically reload to show the newly created work item
Tips:
  • Choose the correct prefix to categorize your work item (e.g., "Xeelo mobile" for mobile-specific features)
  • Be specific in the title - it helps with searching and filtering in Azure DevOps
  • For bugs, always set an appropriate severity level
  • Use the description field for detailed reproduction steps or acceptance criteria

Creating Child Tasks

When in Read-Write mode, you can create child tasks directly from the application:

Prerequisites:
  • Your PAT must have Work Items: Read & Write scope
  • You must select Read-Write permission when entering your PAT
  • The button appears next to Feature or Bug titles when you hover over them

How to create a child task:

  1. Hover over work item title: Move your cursor over any Feature or Bug title
  2. Open the modal: Click the button that appears next to the title
  3. Fill in Title: Enter a descriptive task title (required)
  4. Description (optional): Add detailed information about the task
  5. Assigned To: Select an assignee or leave as "Unassigned" (default)
  6. Review & Submit: Check the parent work item info at the top and click + Create

After creation:

  • A success modal displays with the Task ID and a link to Azure DevOps
  • Click Open in DevOps to view the task in Azure DevOps
  • The task is automatically linked as a child to the parent Feature or Bug
  • The page automatically reloads to show the newly created task
  • The new task appears in the correct position based on sorting rules (status, then alphabetically)

Changing Work Item Status

When in Read-Write mode, you can quickly change the status of any work item directly from the application:

Prerequisites:
  • Your PAT must have Work Items: Read & Write scope
  • You must select Read-Write permission when entering your PAT
  • A small icon appears on status badges when you hover over them

How to change status:

  1. Hover over status: Move your cursor over any status badge (e.g., Active)
  2. Click the badge: The entire badge is clickable - a small icon appears to indicate editability
  3. Select new status: A modal appears with available status options for that work item type
  4. Confirm change: Click on the desired status to apply the change immediately

Available statuses by work item type:

  • Bug & Feature: Evaluation, New, Active, On Hold, Closed
  • Task: New, Active, On Hold, Closed
Immediate Update:
  • The status is updated immediately in Azure DevOps
  • The badge updates in real-time without page reload
  • A success notification confirms the change
  • The current status is highlighted in green when you reopen the modal

Important notes:

  • You can only change statuses that are valid transitions in Azure DevOps
  • The feature works for all work items: Bugs, Features, and Tasks (including child tasks)
  • Changes are logged in Azure DevOps history with your user account
  • If an error occurs, you'll see an error notification with details

Changing Bug Severity

When in Read-Write mode, you can quickly change the severity of any Bug directly from the application:

Prerequisites:
  • Your PAT must have Work Items: Read & Write scope
  • You must select Read-Write permission when entering your PAT
  • Severity is only available for Bugs, not Features or Tasks
  • A small icon appears in the top-right corner of severity badges when you hover over them

How to change severity:

  1. Hover over severity badge: Move your cursor over the severity badge (second badge for bugs, e.g., 3)
  2. Click the badge: The entire badge is clickable - a small icon appears in the top-right corner
  3. Select new severity: A modal appears with available severity options (1-4)
  4. Confirm change: Click on the desired severity to apply the change immediately

Available severity levels:

  • 1 Critical - System unusable, blocks critical functionality
  • 2 High - Major feature affected, workaround exists
  • 3 Medium - Minor feature affected (default)
  • 4 Low - Cosmetic issue, minimal impact
Immediate Update:
  • The severity is updated immediately in Azure DevOps
  • The badge updates in real-time without page reload
  • A success notification confirms the change
  • The current severity is highlighted in green when you reopen the modal

Understanding Priority vs Severity:

  • Priority - How soon the bug should be fixed (business urgency)
  • Severity - How serious the bug's impact is (technical impact)
  • Example: A typo on the homepage could be low severity but high priority (for marketing reasons)
  • Example: A rare crash in an admin tool could be high severity but low priority (affects few users)

Applies to: Bugs only (Features and Tasks do not have severity)

Conventional Commits Format

When you copy a work item title to clipboard, it is automatically formatted according to the Conventional Commits specification.

Format Structure

The copied format follows this structure:

<type>(<scope>): <work_item_id> <description>
Type
  • feat - Used for Features (new functionality)
  • fix - Used for Bugs (bug fixes)
  • Other work item types use their lowercase name as the type
Scope

The scope is currently empty (shown as ()) and can be filled manually or defined by logic later. Scope provides additional contextual information about the commit.

Work Item ID

The work item ID from Azure DevOps is included in the description, followed by the work item title.

Description Processing

The work item title is processed before copying:

  • Any prefix before " - " (space, dash, space) is automatically removed
  • Example: "Xeelo - calendar week start day" → "calendar week start day"
  • The remaining title is converted to lowercase
  • Spaces are preserved (not replaced with underscores)
Examples
Example outputs:
  • Feature: Original title "Xeelo - Calendar Week Start Day" → Copied: feat(): 123 calendar week start day
  • Bug: Original title "Xeelo mobile - Login Button Not Working" → Copied: fix(): 456 login button not working
  • Feature (no prefix): Original title "Calendar Week Start Day" → Copied: feat(): 123 calendar week start day
Benefits:
  • Automatically generates commit messages in a standardized format
  • Compatible with tools that parse Conventional Commits (e.g., for CHANGELOG generation)
  • Makes it easier to track which commits relate to which work items
  • Follows industry-standard commit message conventions

Reference: Learn more about Conventional Commits at conventionalcommits.org
